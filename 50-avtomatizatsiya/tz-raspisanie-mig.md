## 1. Проблема и цель

**Проблема.** Расписание разбросано по нескольким Google-таблицам, актуальность
не гарантирована.

**Следствие.** Путаница в датах, лишние операционные задачи у сотрудников,
падение скорости работы всех отделов.

**Цель.** Один источник правды по расписанию и автоматическое появление мероприятий
в Google Календаре вместе с Zoom-ссылкой.

**Границы задачи.** Бот не управляет регистрациями, не шлёт напоминания участникам
и не заменяет CRM. Он делает одно: превращает сообщение сотрудника в событие календаря
с корректной ссылкой.

---

## 2. Архитектурный принцип

> **Телеграм-канал — источник правды. Календарь — его проекция.**

Канал ведёт себя как журнал: сообщения только добавляются и правятся, ничего не теряется.
Календарь можно в любой момент пересобрать из канала заново.

Из этого следуют два обязательных свойства:

- **Идемпотентность.** Повторная обработка одного и того же сообщения не создаёт
  второе событие и второй Zoom.
- **Восстанавливаемость.** Есть команда полной пересборки календаря из истории канала.

Схема:

```
сотрудник → сообщение в канале «Расписание МИГ»
                      │
              бот читает обновления
                      │
        ┌─────────────┼──────────────┐
        ▼             ▼              ▼
   разбор шаблона  Zoom API     Google Calendar API
        │             │              │
        └─────► ответ ботом в канал: ✅ или ⚠️ с указанием ошибки
```

## 3. Шаблон сообщения

**Это центральная часть ТЗ.** От строгости шаблона зависит, будет система работать
или превратится в источник новых ошибок.

### 3.1 Создание мероприятия

```
#расписание
Название: День открытых дверей для практикующих
Направление: события
Дата: 29.09.2026
Время: 17:00-19:00
Часовой пояс: CET
Формат: онлайн
Зум: создать
Ведущие: Иванова, Петров
Комментарий: ссылка уходит участникам в рассылке
```

| Поле | Обязательно | Формат | Значение по умолчанию |
|---|---|---|---|
| `#расписание` | да | хэштег первой строкой | — |
| Название | да | текст | — |
| Направление | да | из справочника (раздел 13, вопрос 2) | — |
| Дата | да | ДД.ММ.ГГГГ | — |
| Время | да | ЧЧ:ММ-ЧЧ:ММ | — |
| Часовой пояс | нет | CET / MSK / UTC | **CET** |
| Формат | нет | онлайн / очно / гибрид | онлайн |
| Зум | нет | `создать` · `нет` · название постоянной ссылки | `нет` |
| Ведущие | нет | текст через запятую | — |
| Комментарий | нет | текст | — |

**Требования к разбору:**

- регистр названий полей не важен: `дата:`, `Дата:`, `ДАТА:` — одно и то же;
- разделители в поле «Время» — дефис, тире или длинное тире;
- лишние пробелы игнорируются;
- **неизвестное поле — не ошибка**, оно попадает в описание события;
- **отсутствие обязательного поля — ошибка**, событие не создаётся.

### 3.2 Отмена

Ответом на исходное сообщение:

```
#отмена
Причина: болезнь ведущего
```

Либо отдельным сообщением с идентификатором:

```
#отмена
ID: MIG-000123
Причина: перенос на январь
```

### 3.3 Изменение

**Сотрудник редактирует исходное сообщение.** Бот получает событие правки
и обновляет то же самое событие календаря — не создаёт новое.

Это осознанный выбор: правка сообщения — естественное действие в Телеграме,
и ей не нужно учить. Отдельного хэштега для изменений не вводим.

## 4. Функциональные требования

### FR-1 · Чтение канала

Бот добавлен администратором канала «Расписание МИГ» и получает обновления
`channel_post` и `edited_channel_post`.

- **Режим по умолчанию — long polling в реальном времени.** Заявленные в задаче
  5 минут считаем максимально допустимой задержкой, а не целевой: реальное время
  реализуется проще и работает лучше.
- **Ограничение, которое надо учесть:** Telegram хранит необработанные обновления
  около 24 часов. Если бот лежал дольше, сообщения из очереди теряются.
  Поэтому обязателен FR-8.

### FR-2 · Разбор и валидация

Разбор по разделу 3. При ошибке событие **не создаётся**, бот отвечает в канал
ответом на исходное сообщение:

```
⚠️ Не создано
Поле «Время»: не разобрано значение «17.00-19». Ожидается ЧЧ:ММ-ЧЧ:ММ.
Исправьте это сообщение — бот подхватит правку сам.
```

**Правило: в ответе всегда указывается конкретное поле и что именно ожидается.**
«Ошибка формата» без деталей — не принимается.

### FR-3 · Создание Zoom

Если `Зум: создать` — вызвать Zoom API, создать встречу на дату и время события.

- тема встречи = название мероприятия;
- длительность = из поля «Время»;
- часовой пояс — IANA-идентификатор, не смещение (раздел 6);
- параметры встречи (зал ожидания, вход по ссылке, запись) — из конфигурации,
  единые для всех, см. вопрос 5.

Если указано название постоянной ссылки — подставить её из справочника (раздел 5),
Zoom API не вызывать.

Если `Зум: нет` или поле отсутствует — ссылки нет.

### FR-4 · Создание события в календаре

- заголовок = название;
- время = дата, время, часовой пояс;
- описание = ведущие, комментарий, нераспознанные поля, ссылка на исходное
  сообщение в канале;
- **Zoom-ссылка — по правилу из вопроса 4** (в поле «Место», в описании
  или не публикуется вовсе);
- в `extendedProperties.private` записываются `tg_message_id`, `zoom_meeting_id`,
  `mig_id` — по ним событие находится при повторной обработке.

### FR-5 · Подтверждение в канал

Ответом на исходное сообщение:

```
✅ MIG-000123 · создано
29.09.2026 · 17:00-19:00 CET
Zoom: https://zoom.us/j/... (id 812 3456 7890)
Календарь: <ссылка на событие>
```

**Без подтверждения система бесполезна:** сотрудник не должен гадать, сработало или нет.

### FR-6 · Изменение

При `edited_channel_post` найти событие по `tg_message_id` и обновить.

- изменились дата или время и Zoom создавался ботом → обновить и встречу Zoom;
- события не найдено → создать новое и сообщить об этом в ответе;
- ответ: `♻️ MIG-000123 · обновлено` с перечнем изменившихся полей.

### FR-7 · Отмена

- событие переводится в статус `cancelled`, **не удаляется**;
- в заголовок добавляется префикс `ОТМЕНЕНО:`;
- если Zoom создавался ботом — встреча удаляется;
- ответ: `🚫 MIG-000123 · отменено. Причина: ...`

Отмена, а не удаление: у тех, кто уже добавил событие себе, оно останется —
и они увидят отмену, а не молча пропавшую встречу.

### FR-8 · Пересборка

Команда администратора `/resync` и `/resync <дата с>`:

- бот перечитывает историю канала и приводит календарь в соответствие;
- ничего не дублирует за счёт `tg_message_id`;
- по завершении отчитывается: сколько создано, обновлено, отменено, сколько ошибок.

**Это страховка на случай простоя дольше 24 часов и главный инструмент восстановления.**

### FR-9 · Проверка пересечений

Перед созданием бот проверяет:

- **пересечение по постоянной ссылке** — две встречи на одном линке в одно время;
- **пересечение по хосту Zoom** — см. раздел 6, ограничение по параллельным встречам;
- дубль: то же название в те же дата и время.

При обнаружении — **предупреждение в ответе, но событие создаётся**:

```
✅ MIG-000123 · создано
⚠️ Внимание: постоянная ссылка «Лекторий» уже занята 29.09 с 17:00 — MIG-000117
```

Блокировать не нужно: иногда это осознанно. Но не сказать — нельзя.

### FR-10 · Права

Обрабатываются сообщения только от авторов из белого списка.
Сообщение от постороннего — игнорируется, в лог пишется попытка.

## 5. Справочник постоянных ссылок

Хранится в репозитории файлом `links.yml`, меняется через pull request —
чтобы изменения были видны и обратимы:

```yaml
links:
  - name: Лекторий
    url: https://zoom.us/j/000000000
    host: lektorij@mig.institute
    note: общий зал для бесплатных лекций
  - name: БК-поток-1
    url: https://zoom.us/j/111111111
    host: bk1@mig.institute
```

Команда `/links` выводит список в канал.
Название в сообщении сверяется без учёта регистра.

## 6. Время и часовые пояса

**Это самое вероятное место будущих ошибок, поэтому вынесено отдельно.**

- Внутри системы всё хранится в UTC.
- Пользователю всё показывается в часовом поясе события.
- **Используются IANA-идентификаторы** (`Europe/Podgorica`), а не фиксированные
  смещения. `CET` в шаблоне — это ярлык для IANA-зоны из конфигурации.
- Переход на летнее время обрабатывается библиотекой, не вручную.
- В подтверждении FR-5 время печатается с явным указанием пояса.

**Обоснование.** Институт работает в CET, студенты в 50 странах, а расхождение
в час на онлайн-событии означает, что половина группы не пришла.

**Ограничение Zoom, которое надо учесть в FR-9.** Лицензированный пользователь Zoom
по умолчанию не может вести две встречи одновременно. Если у института один-два
хост-аккаунта, а параллельных мероприятий больше — часть встреч не запустится.
Поэтому в конфигурации задаётся пул хост-аккаунтов, а бот выбирает свободный
на нужное время. **Сколько хост-аккаунтов есть — вопрос 3.**

## 7. Доступы и безопасность

**Пункт исходной постановки «дать api ключ Zoom Тине» предлагаю заменить.**
Ключи не должны ходить через переписку и не должны быть у людей, которым
они не нужны для работы.

| Что | Кто выдаёт | Кому | Как |
|---|---|---|---|
| Telegram bot token | Тина создаёт бота | разработчику | через менеджер секретов |
| Zoom Server-to-Server OAuth | администратор Zoom | **напрямую в секреты деплоя** | Тине доступ не требуется |
| Google Calendar | администратор Workspace | сервисному аккаунту | календарь расшарен на его адрес |
| Репозиторий | разработчик | Тине — доступ на чтение | GitHub |

**Требования:**

- **JWT-приложения Zoom не используются — они отключены.** Только Server-to-Server OAuth,
  минимально необходимые права на работу со встречами;
- Google — сервисный аккаунт, нужные календари расшарены ему с правом изменения событий.
  Права на весь Workspace не запрашиваются;
- секреты в `.env` или секретах Docker, **в репозиторий не попадают** — `.gitignore`
  и проверка на секреты в CI;
- белый список авторов — в конфигурации;
- **все действия бота логируются** в формате, принятом для платформы:
  кто · что сделал · какие объекты затронуты · результат.

## 8. Стек и инфраструктура

Предлагаемый; разработчик вправе предложить другой с обоснованием.

| Слой | Решение |
|---|---|
| Язык | Python 3.12 |
| Telegram | `aiogram` или `python-telegram-bot` |
| Google | `google-api-python-client` + сервисный аккаунт |
| Zoom | HTTP-клиент, Server-to-Server OAuth, обновление токена по сроку |
| Хранилище | SQLite — достаточно, объёмы десятки событий в месяц |
| Запуск | Docker + docker compose, рестарт при падении |
| Конфигурация | `.env` + `links.yml` + `config.yml` |
| Логи | stdout + файл с ротацией |

**Альтернатива для быстрого старта:** тот же сценарий собирается в n8n за день.
Минус — сложнее версионировать и тестировать. Рекомендую код в репозитории:
логика разбора шаблона и идемпотентность в визуальном конструкторе быстро
становятся неподдерживаемыми.

## 10. Критерии приёмки

Проверяются на живом канале, каждый пункт — отдельным тестом.

| # | Сценарий | Ожидаемый результат |
|---|---|---|
| 1 | Корректное сообщение с `Зум: создать` | событие в календаре, Zoom создан, ✅ в канале с обеими ссылками |
| 2 | Сообщение с постоянной ссылкой по названию | ссылка подставлена, Zoom API не вызывался |
| 3 | Пропущено поле «Дата» | событие не создано, ⚠️ с указанием именно этого поля |
| 4 | Правка времени в исходном сообщении | то же событие обновлено, **дубля нет**, Zoom перенесён |
| 5 | `#отмена` ответом | статус cancelled, префикс ОТМЕНЕНО, Zoom удалён |
| 6 | Два мероприятия на одну постоянную ссылку внахлёст | оба созданы, во втором — предупреждение |
| 7 | Бот остановлен на сутки, затем `/resync` | календарь приведён в соответствие, дублей нет |
| 8 | Сообщение от автора вне белого списка | проигнорировано, запись в логе |
| 9 | Событие в день перехода на летнее время | время в календаре и в Zoom совпадает с указанным в сообщении |
| 10 | Один и тот же текст отправлен дважды | два события — это разные сообщения. Предупреждение о дубле в ответе |

**Пункты 4, 7 и 9 — ключевые.** Именно на них ломаются такие системы.

## 11. Этапы

| Этап | Содержание | Результат |
|---|---|---|
| **0. Подготовка** | канал, бот, репозиторий, доступы, ответы на вопросы раздела 13 | можно начинать |
| **1. Ядро** | чтение канала, разбор, календарь, подтверждения | события появляются, Zoom вручную |
| **2. Zoom** | создание встреч, постоянные ссылки, пул хостов | ссылки автоматически |
| **3. Надёжность** | правки, отмены, `/resync`, проверка пересечений | приёмка по разделу 10 |
| **4. Эксплуатация** | инструкция для сотрудников, шаблон закреплён в канале | передача в работу |

**Этап 1 уже решает исходную проблему** — единое актуальное расписание.
Если сроки поджимают, сокращать надо этап 2, а не 3: без правок и пересборки
система развалится через месяц.

## 13. Вопросы, блокирующие старт

**На них нужны ответы до начала работ.**

1. **В какой календарь пишем?** Один общий или несколько по направлениям?
   Кому он виден — только сотрудникам, или есть публичный?
2. **Справочник направлений.** Какие значения допустимы в поле «Направление»:
   БК, специализации, ППК, группы, события, лекции — или другой список?
3. **Сколько хост-аккаунтов Zoom** и какие у них лицензии? От этого зависит,
   сколько параллельных мероприятий система вообще может обслужить (раздел 6).
4. **Где публикуется Zoom-ссылка?** Если календарь видят не только сотрудники,
   ссылка в описании — это открытый доступ на мероприятие.
   Предлагаю: во внутреннем календаре ссылка есть, в публичном — нет.
5. **Единые настройки встреч Zoom:** зал ожидания, вход по ссылке или регистрация,
   автозапись. Одинаковые для всех или зависят от типа мероприятия?
6. **Белый список авторов.** Кто именно имеет право публиковать расписание?
   Отдельно: **в канале нужно включить подписи авторов**, иначе технически
   невозможно определить, кто именно опубликовал сообщение, — а без этого
   не работают ни белый список, ни журнал действий.
7. **Что делать со старыми Google-таблицами?** Переносим историю или начинаем
   с чистого листа с фиксированной даты? Рекомендую второе: перенос
   неактуальных данных воспроизведёт исходную проблему.

## 14. Чего я не знаю

1. Тип аккаунта Google — Workspace или обычный. От этого зависит способ выдачи
   доступа сервисному аккаунту.
2. Лицензии Zoom и наличие опции параллельных встреч.
3. Сколько мероприятий в месяц проходит через расписание — от этого зависит,
   хватит ли SQLite и не упрёмся ли в лимиты API.
4. Есть ли у института сервер для размещения бота и кто будет его обслуживать
   после сдачи.
